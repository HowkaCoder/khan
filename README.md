# khan

Учебная мини биржа на Go. Сейчас тут можно создавать лимитные заявки на покупку и продажу, исполнять их и отменять остаток.

Мне хотелось выйти за рамки обычного CRUD и разобраться, как вообще работают такие системы. Как сводятся заявки, где хранятся деньги, что происходит при повторной доставке сообщения и как восстановить стакан после падения процесса.

Для настоящих денег проект пока не подходит. Здесь нет авторизации, пополнения тестовые. Некоторые вещи специально оставлены простыми.

## Как все устроено

Есть три основных сервиса. API, engine и settlement. У каждого своя работа.

API принимает запрос пользователя. Например, купить 3 штуки по цене не дороже 101. Проверяет данные и резервирует нужную сумму в PostgreSQL. Потом сохраняет заявку и команду в таблицу outbox. Все это происходит внутри одной транзакции. Если что то не получилось, изменения откатываются.

Outbox нужен, чтобы не потерять команду между базой и брокером. Если сначала сохранить заявку, а потом отдельно отправлять сообщение, процесс может упасть как раз между этими действиями. Поэтому сначала сохраняем все в базе. Relay потом читает outbox и отправляет команды в NATS JetStream.

Engine получает команды из JetStream и передает их стакану. Для каждой торговой пары запускается свой движок. Сам стакан ничего не знает про HTTP, PostgreSQL или NATS. Он работает с заявками в памяти и возвращает результат.

В стакане две стороны. Bids для покупок, asks для продаж. Покупки идут от большей цены к меньшей, продажи наоборот. На одинаковой цене первой исполняется заявка, которая раньше поступила.

Сначала новая заявка пытается исполниться об встречные предложения. Если что то осталось, остаток встает в очередь по своей цене. Сделка проходит по цене заявки, которая уже стояла в стакане.

После обработки engine публикует события. Settlement читает их и проводит изменения по деньгам. Списывает резерв, начисляет актив покупателю и деньги продавцу. Если покупатель получил цену лучше своего лимита, разница возвращается на доступный баланс.

## Деньги и повторы

Все суммы внутри системы хранятся в int64. Без float64. Например, цена 101.50 превращается в 10150 минимальных единиц.

У баланса есть available и held. Available можно использовать, held уже зарезервирован под заявки.

Сообщение может прийти повторно. Поэтому у сделки есть постоянный идентификатор, а обработка в базе сделана идемпотентной. Повтор одного события не должен создавать повторное списание.

Для создания заявки через API нужен заголовок Idempotency-Key. Если повторить запрос с тем же ключом и теми же параметрами, второй заявки и второго резерва не будет.

## Если движок упал

Engine периодически сохраняет snapshot стакана в PostgreSQL. В нем находятся заявки, их очередь, остатки и номер последней обработанной команды.

После запуска движок загружает snapshot и дочитывает команды из JetStream. При восстановлении проверяются структура сохраненных данных и хеш.

Но история команд не бесконечная. Сейчас она хранится 7 дней. Если нужная часть истории уже удалена, движок остановится с ошибкой. Самостоятельно придумать потерянные команды он не может.

## Запуск

Нужны Docker с Compose v2 и make. Для тестов и генератора нагрузки нужен Go 1.24 или новее. Для скриптов также нужны curl и python3.

Из корня проекта.

```bash
go mod download
go mod verify
make up
```

Проверить сценарий покупки и продажи.

```bash
make smoke
```

Посмотреть логи.

```bash
make logs
```

Остановить сервисы, сохранив данные.

```bash
make down
```

Удалить контейнеры вместе с данными.

```bash
make reset
```

## Проверки

Обычные тесты.

```bash
make test
```

Интеграционные тесты с запущенными PostgreSQL и NATS. Для них используется отдельная тестовая база.

```bash
make test-int
```

Fuzz тесты для поиска неожиданных случаев.

```bash
make fuzz
```

Замеры скорости и выделения памяти.

```bash
make bench
```

Проверка восстановления после принудительной остановки движка.

```bash
make crash-demo
```

Проверка балансов, резервов и финансовых проводок.

```bash
make verify
```

## Что пока ограничено

Авторизации нет. Account ID передает сам клиент, поэтому выставлять такой API в открытый доступ нельзя.

Пополнения тестовые. Это не интеграция с платежной системой. Их можно отключить через DEPOSITS_ENABLED=false.

Для одной пары должен работать один активный engine. Relay тоже один активный. Для этого используются блокировки PostgreSQL, но полноценного механизма fencing пока нет.

Список уже известных заявок растет со временем. Snapshot сохраняется в цикле движка и на большом стакане может задерживать обработку.

Пока нет рыночных заявок, комиссий, риск лимитов и горячего резервного движка. В Docker Compose используются тестовые пароли, NATS без авторизации и одна реплика сообщений.

Go.sum нужно проверить через go mod download и go mod verify в обычном окружении с доступом к инфраструктуре Go.
